# Git conflict resolution

merge、rebase、cherry-pick などで Git 競合を解消するときに使う。

競合を機械的に消すことではなく、両側の変更意図を保った解決と検証を目的にする。

## ベースの最新化と rebase

作業ブランチをベースブランチへ追従させる競合解消では、次の順に進める。
すでに merge、rebase、cherry-pick が進行中の場合は、新しい操作を始めず、進行中の操作の解消手順へ進む。

1. 対象リポジトリ、作業ブランチ、取り込み先のベースブランチ、fetch/push 先を確認する。
   PR がある場合はその base を使い、default branch と同じだと推測しない。
   作業ブランチの worktree が clean であることを確認し、変更や未追跡ファイルがあれば保全してから進める。
2. 認証と SSH 鍵の確認は、利用可能なら `git-workflow` の手順に従い、リモートのベースと作業ブランチを fetch する。
   rebase 前のローカル HEAD、fetch したリモートベースの SHA、既存のリモート作業ブランチの SHA を記録する。
   リモート作業ブランチがローカル HEAD の祖先でなければ、未取り込みの変更を確認するまで停止する。
3. ローカルのベースブランチを、対応するリモートブランチへ fast-forward のみで最新化する。
   別 worktree で checkout されている場合は、その worktree が clean で他の操作に使用中でないことを確認して更新する。
   分岐や使用中の worktree により安全に更新できなければ停止し、reset や強制的な参照更新で合わせない。
4. 作業ブランチの worktree で、最新化したローカルのベースブランチを指定して `git rebase <base-branch>` を実行する。
   競合したら以下の解消手順に従う。

## 解消手順

1. 競合操作、対象 branch、共通祖先、競合ファイルを確認する。
   未関係のローカル変更がある場合は、競合解消と混ぜずに保全する。
2. base、現在の branch 側、取り込む側の各変更を読む。
   競合した理由と採用すべき振る舞いを判断する。
3. `ours` または `theirs` の一括選択を、内容確認の代わりに使わない。
4. 意図が矛盾する、仕様が不明、またはデータ喪失・互換性に影響する場合は停止する。
   方針を確認してから続ける。
5. 解消後は競合マーカーと差分を確認し、影響範囲に応じた検証を実行する。
   競合操作の継続・abort・commit は、結果とユーザーの依頼範囲に従う。

## rebase 後の push

対象ブランチへの push がユーザー本人の依頼・承認範囲に含まれる場合、次の条件をすべて満たせば、`--force-with-lease` による更新について追加承認を求めずに実行できる。

- 対象が当該セッション専用の作業ブランチであり、作成時の記録やユーザーの指定から専用と確認できる。
  ブランチ名の接頭辞だけでは判断せず、ベースブランチ、共有ブランチ、他セッションが使用するブランチ、専用か不明なブランチには適用しない。
- この手順による rebase が完了し、作業ツリーが clean で、競合マーカー・最終差分・必要な検証を確認済みである。
  rebase 前後のコミット列を `git range-diff` などで比較し、対象外の変更やコミットの欠落がないことを確認する。
- push 先が確認済みの同一リポジトリの作業ブランチであり、rebase 前に記録したリモート SHA を期待値として固定できる。
  通常ローカル経路で認証・SSH 鍵を確認し、直前に読み戻したリモート SHA が期待値と一致することを確認する。

送信先の branch と期待 SHA を省略しない形式で、一つの branch だけを更新する。

```sh
git push --force-with-lease=refs/heads/<work-branch>:<recorded-remote-sha> <remote> HEAD:refs/heads/<work-branch>
```

`--force`、`+` 付き refspec、期待 SHA を省略した `--force-with-lease` は使わない。
lease の不一致やリモート更新を検知したら停止し、期待 SHA の取り直しだけで再試行しない。
結果不明時は再送せずリモートを読み戻し、成功時も送信先の SHA がローカル HEAD と一致することを確認する。
既存 PR がある場合は最新 head を照合し、CI はその head の結果を別途確認する。
進行中だった rebase の再開などで専用性や rebase 前のリモート SHA を確認できない場合も、この追加承認不要の許可は適用しない。

## 境界

- この skill は、ベースの最新化、rebase、競合内容の理解、解消、検証と、上記条件を満たす push を扱う。
- 競合操作に必要な継続以外の commit、PR 本文などの更新、レビュー返信、PR の merge は、この skill だけで実行しない。
- push 自体の承認がない場合や上記条件を満たさない履歴書き換えは、実施せず対象と操作を具体化して確認する。
  リポジトリの保護ルールと自動承認レビューの拒否を回避しない。
